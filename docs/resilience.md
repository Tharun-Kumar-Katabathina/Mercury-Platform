# Resilience and chaos testing (Phase 13)

The claim "Mercury survives failures" is backed by a repeatable experiment, not by argument: `scripts/chaos/run.py` injects each failure into
the **real container stack** (Docker Compose, the same images that ship), watches how the platform behaves, repairs the failure, and then checks
the **state of the system from its databases and Kafka**. The result is [failure-matrix.md](failure-matrix.md), generated by the run.

```bash
scripts/init-secrets.sh                   # once
python3 scripts/chaos/run.py              # everything (about 30 minutes); F01 F05 ... runs only those; --keep leaves the stack up
```

## 1. How it works

- **Stack**: the production-like Compose platform plus `docker-compose.chaos.yml`, which only shortens recovery, outbox and waiting intervals so that
  detection and repair take seconds instead of minutes. Authentication is ON: the harness logs in as an administrator and as a customer.
- **Faults** (all from outside, with the Docker CLI): `SIGKILL` (a crash: no shutdown hooks), `docker pause` (frozen: sockets stay open, nothing answers),
  `docker stop`/`restart`, **packet loss 100 %** and **latency** injected with `tc netem` from a throw-away helper container that shares the victim's network
  namespace (the service images stay unprivileged). Faults are always removed in a `finally`, and the stack is healed between scenarios.
- **Load**: concurrent orders over HTTP with unique idempotency keys; the clients' view (status codes, slowest request) is recorded.
- **Verdict**: not "did the HTTP calls succeed" but the **invariants**, read directly from PostgreSQL and Kafka after the system settles:

| Invariant | Meaning |
|---|---|
| Stock is conserved | per product, `available + reserved = initial`, and `available` never below 0 (no overselling) |
| Nothing stranded or phantom | reserved quantity equals exactly what CONFIRMED orders hold |
| Every order is final | CONFIRMED or CANCELLED; every saga CONFIRMED or CANCELLED (none COMPENSATING, AWAITING, RESERVING, RECOVERY_FAILED) |
| Nothing left behind | both outboxes fully published |
| No duplicate effect | no order announced as confirmed twice; one reservation decision per asynchronous order |

Each scenario also asserts its own expectation (for example "refused with 503 and nothing saved", "stayed PENDING, no guess").

When a scenario fails, the log of every container is saved at that moment in `target/chaos-diagnostics/<scenario>/` (not tracked; the
nightly run attaches it as `chaos-diagnostics`), before a later scenario can recreate a container and lose it.

## 2. The scenarios

| # | Failure | What it demonstrates |
|---|---|---|
| F01 | Inventory killed under load | bounded fast failures (circuit breaker), no corruption, resumes after restart |
| F02 | Order killed mid-saga | recovery finishes interrupted sagas; no stranded stock |
| F03 | Product killed | refused `503` before anything is saved |
| F04 | Notification killed | ordering unaffected; every notification arrives exactly once afterwards |
| F05 | Kafka frozen | ordering unaffected; events wait in the outbox and are published in full |
| F06 | Kafka restarted under load | no event lost, none duplicated |
| F07 | PostgreSQL stopped | `503 DATABASE_UNAVAILABLE`, readiness down, automatic recovery |
| F08 | PostgreSQL restarted under load | requests wait (bounded) and succeed |
| F09 | Network partition (Inventory) | calls time out in bounded time; resumes when healed |
| F10 | Latency above the read timeout | ambiguous reservations resolved by lookup and released |
| F11 | Inventory killed while consuming commands | redelivery; exactly one reservation per order |
| F12 | Order killed right after accepting orders | the outbox still delivers every command |
| F13 | Duplicate command ×3 | one reservation, one reply |
| F14 | Unknown / out-of-order / repeated replies | all ignored; a confirmed order cannot be un-confirmed |
| F15 | Reservation timeout, then a late reservation | cancelled with `RESERVATION_TIMEOUT`; the late stock is detected and released |
| F16 | Inventory frozen at the deadline | **no cancellation on a guess**; retried with backoff; resolved when it thaws |
| F17 | Poison messages | dead-lettered; nothing behind them blocked |
| F18 | User Service killed | logged-in customers keep ordering (tokens verified locally); new logins refused |
| F19 | Flood of forged tokens | all refused `401`; real orders unaffected and fast |

## 3. What the experiments found (and what was changed)

The harness found real problems, which is its purpose. Each is fixed and covered by a test:

1. **A recovered service tripped the circuit breaker (F04, found when scenarios ran back to back).** The breaker measured the last 20 *calls*; five failures from an
   outage were still in that window after Product had fully recovered, so the tenth call saw a 50 % failure rate and opened the circuit on a healthy service. Fix:
   a configurable **time-based window** (`ORDER_*_CB_WINDOW_TYPE=TIME_BASED`, 20 seconds), used by the deployed configuration, so an outage ages out by itself.
   `DownstreamGuardTests` shows both behaviours side by side. (A failed Product call also left no trace in the log: it now logs its cause.)
2. **`500` while the database was down (F07).** Infrastructure failure was reported as a server bug. Services now answer `503 DATABASE_UNAVAILABLE` with
   `Retry-After`, so clients and load balancers can tell "retry shortly" from "defect".
3. **A harness expectation, not a platform defect (F11).** An asynchronous order whose reply takes longer than the waiting deadline is *correctly* cancelled
   (`RESERVATION_TIMEOUT`) and its late reservation released; the crash-recovery scenarios therefore run with a long deadline and the timeout scenarios with a
   short one. The platform behaved as designed; the test had to say which behaviour it was testing.
4. **A test that did not overlap its fault (F08)**: the load finished before the PostgreSQL restart; it now outlasts it, and records how long requests waited.

Every one of these was found by running the system, not by reading it.

## 4. Failure behaviour in one table

| Failure | The platform's answer | Customer sees |
|---|---|---|
| Inventory down (synchronous) | circuit opens; fail fast; ambiguous reservations resolved after | `503`, retry later |
| Inventory down (asynchronous) | command waits in Kafka; order waits, never guessed | `202`, then confirmed when it returns |
| Product down | refused before saving | `503` |
| Notification / Recommendation down | no effect on orders; they catch up from Kafka | nothing |
| Kafka down | outbox holds events (unbounded, ordered); ordering unaffected | nothing |
| PostgreSQL down | not-ready, `503` + `Retry-After`, automatic reconnect, sagas resume | `503`, retry shortly |
| Order crashes | recovery finishes every interrupted saga | retried request gets the same order |
| Duplicate / replayed message | idempotent consumers and idempotent keys | nothing |
| User Service down | tokens verified locally; only new logins fail | existing sessions unaffected |
| Redis down | cache miss; the database answers | slightly slower |
| Qdrant down | `503` for similar/personalised only; no data lost | recommendations unavailable |

## 5. Limits of this evidence

- The failures are injected on **one machine** (Docker Desktop): real network behaviour, multi-node partitions, disk and clock faults, and a multi-broker Kafka
  are not exercised; Kafka and PostgreSQL are single instances, so "Kafka restarted" tests recovery of one broker, not leader election.
- The scenarios are deterministic experiments, not a continuous random-fault generator; combinations (two failures at once) are limited to what a scenario sets up.
- Timings (recovery seconds) depend on the host; they show the order of magnitude, not an SLA.
- The matrix is regenerated by every run (nightly in CI); a committed copy is a snapshot from the run named inside it.
